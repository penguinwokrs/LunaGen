# 初回メッセージを「相手に刺さり、返したくなる」設計に組み直す

2026-08-01

## 問題

初回メッセージ生成で、**相手のプロフィールに書かれていない食べ物の話題が頻繁に出る**。
相手固有の内容に触れないため、誰に送っても成立する汎用文になり、返信につながらない。

## 原因

### 原因1: 需給マッチ分析が構造化フィールドしか見ていない

`utils/demand-supply.ts` の `computeDemandSupply` が突き合わせるのは、
関係目的コード・S/M象限・年齢・地域・体型・喫煙・パートナー状況・`q_*` スコアだけである。
**相手の自由記述（自己紹介本文・嗜好本文・求める条件本文）を一切読んでいない。**
自由記述は `{target_info_clean}` に生のまま貼られるのみ。

結果として分析が出力する「噛み合う点」はこうなる:

```
- [生活条件/相互] 年齢がお互いの希望条件に合致 — 直接「条件に合う」とは言わず前提として扱う。
- [生活条件/相互] 喫煙の希望がお互いに合致 — 生活面の相性として自然に。
```

そして `constants.ts` の `DEFAULT_PROMPT` は「最も噛み合う1〜2点を選ぶ」と指示する。
つまり LLM は「年齢条件が合う」「喫煙が合う」を主役に据えろと命じられている。
これで刺さる文章は書けない。書くことが無いので、無難な話題へ逃げる。

### 原因2: プロンプトが名指しする唯一の具体トピックが「食べ物」

コードベース全体で食に触れているのは `constants.ts:26` の1行だけである。

```
- 初回メッセージで「ご飯行きましょう」「飲みに行きませんか」のような食事・飲みの誘いは禁止（食の好みに触れるのはOK）
```

禁止のつもりの行が焚きつけている。理由は2つ:

1. プロンプト中で名指しされた唯一の具体的な話題が食べ物である（他の指示はすべて抽象語）
2. その唯一の名詞に「触れるのはOK」と明示的な許可が付いている

原因1で「書くことが無い」状態に置かれた LLM が、唯一許可された具体トピックに流れる。
**この行を消すだけでは別の無難な話題に逃げるだけで、原因1が残る限り解決しない。**

### 原因3: 禁止事項は厚いが、書くべきことの手順が薄い

現行プロンプトは禁止事項6項目・制約事項7項目に対し、書き方の指示は
「噛み合う点を具体で示す」「トーンを合わせる」程度しかない。
さらに**相手の自由記述が薄い/空の場合の指示が存在しない**。
Luna では自己紹介が空の相手が珍しくないが、その場合も「200文字以内」だけが与えられるため、
LLM は200字を埋めようとして捏造か無難話題に走る。

## 設計

### 柱1: 素材の優先順位を逆転する

| | 現行 | 変更後 |
|---|---|---|
| 主役 | 需給マッチ分析の噛み合う点 | 相手の自由記述から選んだ固有の一節 |
| 需給マッチ分析（生活条件軸） | 主役候補 | 前提・土台。話題の主役にしない |
| 需給マッチ分析（嗜好・目的・役割軸） | 主役候補 | 話題候補（自由記述に手がかりが無いときの代替） |

`utils/demand-supply.ts` の `formatDemandSupplyHint` の出力を3ブロックに分割する。

- **話題になりうる噛み合い**: 軸が `嗜好` / `目的` / `役割` のもの
- **前提条件（話題にしない。土台として扱う）**: 軸が `生活条件` のもの（年齢・地域・体型・喫煙・パートナー状況）
- **避ける点**: 既存の `avoid` 配列。現行の文面・挙動のまま維持する

生活条件軸の `talkingPoint` は現状「エリアが噛み合う。会いやすさ・距離感に軽く触れられる」のように
話題化を誘う文面になっているため、前提として扱う文面に書き換える。

両ブロックとも該当が無ければそのブロックごと出力しない（現行の空文字返却の挙動は維持）。

`background.ts` が注入するセクション見出しは `# 需給マッチ分析` から
`# プロフィール項目の突き合わせ` に変更し、`DEFAULT_PROMPT` と
`CONTINUOUS_CONVERSATION_PROMPT` 内の「需給マッチ分析」への参照もすべて追随させる。

### 柱2: 「刺さる」を3ステップの手順にする

プロンプトに以下の手順を置く。

```
ステップ1: 相手の自由記述から「その人しか書いていない一節」を1つ選ぶ
  - 具体的な名詞・状況・理由が入っていること
  - 相手が自分から語っていること（＝語りたいこと）
  - 却下: 他の人のプロフィールにも書いてありそうな一般的な表現
ステップ2: そこに自分の側の具体を1つ添える
ステップ3: その一節の「隣」を聞く問いで締める
```

ステップ2が返信率の要である。現行プロンプトには相手の話に触れる指示しかなく、
自分を差し出す指示が弱い。相手からすると「読まれた」だけで「話したい」にならない。

### 柱3: 「返したくなる問い」の条件を明示する

- 相手が既に語っていることの「隣」を聞く（もう一歩先、または理由）
- はい/いいえで終わる問いにしない
- かといって考え込ませない。答えの選択肢を2つ示す形にしてもよい
- 問いは1つだけ（複数質問は尋問になる）

### 柱4: 禁止事項から具体名詞を消す

- 「食事・飲みの誘いは禁止（食の好みに触れるのはOK）」を削除し、
  **「初回で会う約束・日程・場所の話を出さない」** に一般化する。食べ物を名指ししない。
- 新設: **「相手のプロフィールに書かれていない話題を自分から持ち出さない」**。
  素材外の話題を一律で塞ぐ、原因2への直接の栓。

### 柱5: 自由記述が薄い相手のフォールバックを明示する

| 相手の自由記述 | 方針 |
|---|---|
| 十分にある | 柱2の3ステップどおり |
| 薄い（自己紹介が30字未満程度） | 嗜好・役割の方向性に触れ、**自分の具体を先に開示**してから答えやすい問いを1つ置く |
| ほぼ無い | **100文字程度で短く書く**。自分の開示1つと問い1つだけ。長文で埋めない |

「書くことが無いなら短くてよい」を明示することが要点。
現行は200字上限しか与えていないため、素材が無くても200字を埋めようとする。

### 新しい `DEFAULT_PROMPT`

```
あなたはマッチングサイト「Luna」で、いいねに添える初回メッセージを送るユーザーです。
相手のプロフィールを読み込み、「この人は自分のことをちゃんと読んだ」と伝わり、かつ返事を書きたくなるメッセージを作成してください。

# 基本姿勢
- 「分析しました」「条件に合っていますね」のような採点・評価する物言いは一切しない。気づいたら自然に触れている、という体で書く
- ロマンチックな決め台詞（「特別な存在」「運命」「あなただけ」等）や過度に情緒的な表現は使わない。具体的で実務的に

# 最重要ルール: 触れてよい素材の範囲
このメッセージで触れてよい話題は、相手のプロフィール本文（自己紹介・嗜好・求める条件）に書かれていることだけです。
- 相手が書いていない話題を自分から持ち出さない。一般論で埋めるくらいなら短く終わらせること
- 「前提条件」に挙がった項目（年齢・エリア・喫煙・体型等）は話題の主役にしない。これらは会話の土台であって話題ではない

# ステップ1: 主役にする一節を選ぶ
相手の自由記述（自己紹介・嗜好・求める条件の本文）から、その人しか書いていない一節を1つ選ぶ。
- 選ぶ基準: 具体的な名詞・状況・理由が入っている / 相手が自分から語っている（＝語りたいこと）
- 却下する例: 他の人のプロフィールにも書いてありそうな一般的な表現、テンプレ的な挨拶文
- 「避ける点」に挙がった事項（相手のNG等）は選ばない
- 自由記述に手がかりが無い場合に限り、「話題になりうる噛み合い」の嗜好・目的・役割を代わりに使ってよい

# ステップ2: 自分の側の具体を1つ添える
選んだ一節に対して、自分のプロフィールから対応する具体を1つ出す。
- 「僕も〇〇が好きで」で終わらせず、自分がどうなのかを具体で示す
- 相手を読むだけでなく、自分を差し出すこと。これが無いと相手は返す動機を持てない

# ステップ3: 答えやすい問いで締める
- 選んだ一節の「隣」を聞く（相手が書いていることの、もう一歩先や理由）
- はい/いいえで終わる問いにしない。かといって考え込ませない。答えの選択肢を2つ示す形にしてもよい
- 問いは1つだけ。複数質問は尋問になる

# 相手の自由記述が少ない場合
- 薄い（自己紹介が30字未満程度）: 嗜好や役割の方向性に触れ、自分の具体を先に開示してから、答えやすい問いを1つ置く
- ほぼ無い: 100文字程度で短く書く。自分の開示1つと問い1つだけ。書くことが無いなら短くてよく、長文で埋めようとしない

# 禁止事項（厳守）
- 相手のプロフィールに無い話題を持ち出すこと（最重要）
- 「プロフィール拝見しました」「プロフィールを見て」等のテンプレ表現。いきなり本題に入ること
- 相手のNG・拒否事項への言及（「〇〇はしません」と引用して安心させようとするのも逆効果）
- 初回で相手の容姿・表情・身体について具体的に言及すること
- 「ちゃん」「くん」等の馴れ馴れしい呼び方（名前には「さん」を付ける）
- 「そそられる」「興奮する」「ムラムラ」等の直接的な性的興奮を示す表現
- 初回で会う約束・日程・場所の話を出すこと
- 相手が使っていない過激な表現・卑猥な単語を使うこと（相手が使っている用語はそのまま使ってよい）

# 制約事項
- 冒頭の挨拶は相手のトーンに合わせて自然に。「[相手の名前]さん、はじめまして！」の定型でなくてよい
- 相手の文体（カジュアル/丁寧、絵文字の多少）を読み取り、トーンを合わせる
- 最後は必ず疑問符（？）を使った問いかけで締める。「〜ですね」「〜ください」等の平叙文で終わらない
- 対等な目線を保つ。初対面で「受け止めます」「リードします」等の役割宣言はしない
- 文字数は句読点・記号・空白・改行すべて含めて合計200文字以内（厳守。200文字を1文字でも超えたら失格）
- 感情表現には記号の顔文字（(^^), m(_ _)m等）を使わず、絵文字（😊, ✨等）を使用する
- メッセージ本文のみを出力すること。分析過程や補足説明は不要

# 自分のプロフィール
{my_info_clean}

# 相手のプロフィール
{target_info_clean}
```

`CONTINUOUS_CONVERSATION_PROMPT`（会話継続用）は本設計の対象外だが、
柱1で見出しを変えるため「需給マッチ分析」への参照1箇所のみ追随させる。内容は変更しない。

### 生成品質の評価

- 本番と同じ `DEFAULT_PROMPT` / 需給マッチ注入 / 置換ルール適用 / `safetySettings` を通す

**自動チェック（決定論）:**

| 項目 | 基準 |
|---|---|
| 素材外話題 | 食べ物・飲食語彙の辞書に当たる語が、相手プロフィール本文に無いのに出現していないか。辞書はハーネス内に定義し、実際に混入した語を見つけ次第追加する |
| 固有度スコア | メッセージ中の内容語のうち、相手プロフィール本文に出現する語の割合。**合格基準には使わず、旧プロンプトとの比較用の参考指標**とする |
| 文字数 | 200字以内（プレミアム時500字） |
| 末尾 | 「？」で終わる |
| 禁止表現 | 「プロフィール拝見」「ちゃん」「くん」「そそられる」等のリスト |
| NG言及 | 相手の NG 欄の語がメッセージに出現していない |
| 敬称 | 相手の名前を呼ぶ場合「さん」が付いている |

**汎用性テスト（この設計の中心指標）:**

生成したメッセージを**別人のプロフィール**と一緒に LLM に渡し、
「このメッセージはこの人物宛てとして成立するか」を判定させる。
成立してしまうなら、それは誰にでも送れる汎用文である。
コーパスから無作為に選んだ他人3名に対して判定し、成立率を測る。

**LLM審査（相手役になりきらせる）:**

- 「あなたはこのプロフィールの人物です。このメッセージに返信したいと思いますか」5段階＋理由
- 「このメッセージは、あなたのプロフィールを読んだ上で書かれていると感じますか」5段階＋理由

**合格基準:**

- 素材外話題の検出 0件（現行プロンプトでの検出件数をベースラインとして併記する）
- 汎用性テストの他人成立率 20%以下
- 返信意欲の平均 4.0以上、かつ 2以下が10%以下
- 自動チェックの機械項目（文字数・末尾・禁止表現・NG言及・敬称）は全件 pass

### 既存ユーザーの移行

`options.tsx` のプロンプト初期値は `DEFAULT_PROMPT` を参照するため、**未保存**のユーザーは自動で新しくなる。
問題は既に storage に保存済みのユーザーで、放置すると旧プロンプトが使われ続ける。

**未編集なら自動追従する**方式を採る。

- 旧プロンプトを `constants.ts` に `LEGACY_DEFAULT_PROMPT_V1` / `LEGACY_CONTINUOUS_PROMPT_V1` として残す
- `background.ts` の `chrome.runtime.onInstalled`（`reason === "update"` および `"install"`）で移行を実行する
  - `promptTemplate` が未設定、または `LEGACY_DEFAULT_PROMPT_V1` と**完全一致**する場合のみ `DEFAULT_PROMPT` に更新する
  - `continuousPromptTemplate` も同様に `LEGACY_CONTINUOUS_PROMPT_V1` と完全一致する場合のみ更新する
    （柱1の見出し変更で1行だけ変わるため、こちらも移行対象）
  - 一致しなければ**何もしない**。ユーザーが編集した内容は絶対に上書きしない
- 移行の実行有無を `logBG` に記録する（効かなかったときに切り分けられるようにする）
- 判定は `utils/prompt-migration.ts` の純粋関数
  `migratePrompt(stored: string | undefined, legacy: string, next: string): string | null`
  として切り出し、更新不要なら `null` を返す。`utils/prompt-migration.test.ts` でテストする

自分で編集した人には届かないため、設定画面の「デフォルトに戻す」で新プロンプトを取得できる旨を
README に1行追記する。

## 後続作業: 口調プリセット3パターン

本設計の実装後、別Specとして実装する。ユーザーと合意済みの決定事項を記録しておく
（口調ブロックの文面が新 `DEFAULT_PROMPT` の記述に依存するため、本設計を先に確定させる）。

- 設定画面に3枠固定の口調プリセット。各枠は「名前」と「口調の指示文」を自由編集でき、初期値あり
  （丁寧 / フレンドリー / クール）。「デフォルトに戻す」あり
- 口調は文体のみを指定する。禁止事項・文字数・素材の範囲は本体テンプレート側に残す
- 4つ目の選択肢として「指定なし」を用意し、既定にする（アップデートで既存の生成結果を変えないため）
- 設定画面に「既定の口調」セレクタを置き、新しい相手はこれで始まる
- `[ AI ] [ 口調: 丁寧 ▾ ] [ クリア ]`。ドロップダウンで選ぶだけで、生成は従来どおり AI ボタン
- 選択は**相手ごとに記憶**する。キー解決は URL のユーザーID → キャッシュのユーザーID → スレッドID の順、
  どれも取れなければ保存しない。`chrome.storage.local` の `partnerTones` に上限300件、
  `updatedAt` の古い順に間引く
- 枠のIDは `tone1/tone2/tone3` 固定（ラベル変更で相手ごとの記憶が迷子にならないため）
- 指示文が空の枠はメニューに出さない
- プロンプト末尾に口調ブロックを追加する。`{tone_instruction}` があればその位置に差し込む。
  会話継続テンプレートの「ミラーリング最優先」と衝突するため、
  「テンション・文章量のミラーリングは維持し、語り口だけこの指定に従う」と役割分担を明記する
- 判断ロジックは `utils/tone.ts` の純粋関数に寄せ、`utils/tone.test.ts` でテストする
