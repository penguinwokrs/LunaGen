# メッセージの口調プリセット3パターン

2026-08-02

## 要望

設定画面で口調を3パターン事前に登録できるようにする。生成時は「AIで生成」「クリア」の隣に
口調を呼び出すボタンを1つ置き、そこから選ぶ。

## 決定事項（ユーザーと合意済み）

| 論点 | 決定 |
|---|---|
| 口調の中身 | 3枠固定。各枠が「名前」と「口調の指示文」を持ち、どちらも自由編集できる。初期値あり |
| ボタンの挙動 | 口調を切り替えるだけ。生成は従来どおり「AI」ボタン |
| 保持スコープ | 相手ごとに記憶する |
| 新しい相手 | 設定画面の「既定の口調」から始まる |

## 設計

### 1. 口調プリセット（設定画面）

`4. 口調プリセット` セクションを `3. プロンプトテンプレート` の下に新設する。

- 3枠固定。枠のIDは `tone1` / `tone2` / `tone3` で不変。**ラベルを変更しても相手ごとの記憶が迷子にならない**
- 各枠は `label`（メニューに出す短い名前）と `instruction`（プロンプトに差し込む本文）を持つ
- 「デフォルトに戻す」ボタンを置く
- `instruction` が空の枠はメニューに出さない
- 「既定の口調」セレクタを置く。選択肢は「指定なし」＋3枠。**初期値は「指定なし」**

初期値:

| id | label | instruction |
|---|---|---|
| `tone1` | 丁寧 | 敬体（です・ます）で統一し、落ち着いた距離感を保つ。一文はやや長めでも良いが回りくどくしない。絵文字は0〜1個まで。感嘆符は控えめに。 |
| `tone2` | フレンドリー | 敬体をベースにしつつ砕けた言い回しを混ぜ、テンポ良く。一文は短め。絵文字は2〜3個まで自然に使う。 |
| `tone3` | クール | 短い言い切りを中心に、淡々と具体的に書く。感嘆符は使わない。絵文字は0〜1個まで。馴れ馴れしくならない。 |

**口調は文体だけを指定する。** 禁止事項・文字数・素材の範囲は本体テンプレート側に残す。指示文は自由記述なので
内容ルールも書けてしまうが、初期値と設定画面の説明文は文体に寄せる。

**既定を「指定なし」にする理由**: 拡張を更新した瞬間に全ユーザーの生成結果が変わるのを避けるため。
使いたい人だけが選ぶ形にする。

### 2. 生成ボタン横のUI

`[ AI ] [ 口調: 丁寧 ▾ ] [ クリア ]`

- `components/Content/ToneSelector.tsx`（新規）。`GenerateButton` の中に並べる
- ドロップダウンは同じ React ルート内にインラインスタイルで描く（プロフィール改善のシャドウDOMモーダルは大げさなので使わない）
- 項目は「指定なし」＋ `instruction` が空でない枠。選ぶと即保存してラベルが変わるだけ
- 外側クリックと Esc で閉じる
- 生成中（`loading`）は無効化する

### 3. 相手ごとの記憶

キーの解決順:

1. URL のユーザーID（`/user/show/xxx`）→ `u:<id>`
2. URL のスレッドID（`/user/message/xxx`）→ `t:<id>`
3. `luna_last_viewed_user` キャッシュのユーザーID（現在のURLと一致検証済み。既存の `resolveCachedPartner` を再利用）→ `u:<id>`
4. どれも取れない → 既定の口調を表示し、**選んでも保存しない**（その入力欄が生きている間だけ有効）

**URL から決まるものを常に優先する。** キャッシュを先に見ると、メッセージページでは
`resolveCachedPartner` がページ読み込み直後は必ず null を返し（スレッドIDの照合が通らない）、
API キャッシュが届いた後は userId を返すため、同じ相手が `t:` と `u:` の2つのキーに割れる。
「さっき選んだ口調が忘れられている」という症状になる（2026-08-02 のリリース後レビューで判明）。

**評価のタイミング**: 表示用はマウント時とドロップダウンを開く時。
**生成に使う口調は、生成ボタンを押した時点で storage から読み直す。**
React state に持つと、SPA遷移で同じ `textarea` が使い回されたときに前の相手の口調で
生成してしまう（同レビューで判明）。`ToneSelector` は表示と保存だけを担当する。

保存先は `chrome.storage.local` の `partnerTones`:

```ts
{ [key: string]: { toneId: string; updatedAt: string } }
```

上限300件。超えたら `updatedAt` の古い順に捨てる。放置すると際限なく溜まるため。

**割り切り**: 同じ相手でも、プロフィール画面では `u:` キー、メッセージ画面でスレッドしか取れない瞬間は
`t:` キーになり、口調が別枠で記憶されることがある。実際にはメッセージ一覧APIのキャッシュでほぼ `u:` に
寄るので、キーの統合（移行処理）は入れない。

### 4. プロンプトへの差し込み

口調ブロックはプロンプトの**末尾**（プロフィール・会話履歴の後）に追加する。既存のセクション構成を崩さず、
末尾は指示が効きやすいため。テンプレートに `{tone_instruction}` があればその位置に差し込む。

```
# 口調の指定（文体について最優先）
{instruction}
※この指定は、文体・語り口・絵文字の量について、他のすべての指示より優先する。
　相手の文章量やテンションに合わせる指示は維持する（合わせるのは長さと熱量、語り口はこの指定に従う）。
```

**最後の2行が必要な理由**: 現行プロンプトには文体に関する指示が複数ある。

- 初回用: 「相手の文体（カジュアル/丁寧、絵文字の多少）を読み取り、トーンを合わせる」「絵文字（😊, ✨等）を使用する」
- 会話継続用: 「相手の口調・テンション・文章量のミラーリングは他のすべてのルールより優先」

これらと口調指定は正面から衝突する。**語り口・絵文字の量＝口調指定、文章量・テンション＝ミラーリング**と
役割を分けて両立させる。

### 5. データの渡し方

content → background には `toneId` だけを送り、background が storage からプリセット本文を引く。
プリセットの実体を1箇所に閉じ込めるため。`toneId` が未指定・`"none"`・存在しないID・`instruction` が空の
いずれかなら、口調ブロックを差し込まない。

## ファイル構成

| ファイル | 内容 |
|---|---|
| `constants.ts` | `DEFAULT_TONE_PRESETS`、口調ブロックの雛形 |
| `utils/tone.ts`（新規） | 型、相手キーの解決、口調の解決、300件の間引き、ブロック生成。すべて純粋関数 |
| `utils/tone.test.ts`（新規） | 上記のテスト |
| `components/Options/TonePresetSection.tsx`（新規） | 設定画面の3枠＋既定口調＋リセット |
| `components/Content/ToneSelector.tsx`（新規） | ボタンとドロップダウン |
| `components/Content/GenerateButton.tsx` | ToneSelector を並べ、生成時に `toneId` を送る |
| `options.tsx` | TonePresetSection を組み込む |
| `background.ts` | `toneId` を受け取り、口調ブロックを差し込む |
| `utils/message-prompt.ts` | `buildMessagePrompt` に `toneInstruction` を受け取らせる |

判断が要る所はすべて `utils/tone.ts` の純粋関数に寄せ、background と React 側は薄く保つ。
既存の `utils/premium.ts` / `utils/partner.ts` と同じやり方。

## テスト

`utils/tone.test.ts`:

- 相手キーの解決順（URL のユーザーID > キャッシュのユーザーID > スレッドID）
- キーが取れないときは保存しない
- 新しい相手は既定の口調になる
- 上限300件で `updatedAt` の古い順に間引く
- ラベルを変更してもIDで引ける
- `instruction` が空の枠はメニュー候補にならない
- `toneId` が `"none"` / 未知のID / 空文字のとき、口調ブロックを生成しない
- `{tone_instruction}` がある場合はその位置、無い場合は末尾に差し込む

## やらないこと

- 会話継続用プロンプトの内容変更（口調ブロックの差し込みは行うが、テンプレート本文は触らない）
- 3口調を同時生成して比較するUI（プロフィール改善の3択モーダルとは別物にする）
- 口調ごとのプロンプトテンプレート全体の持ち替え

## 未検証の前提

口調指定が実際に生成結果の文体を変えるか、また文体を固定することで
[初回メッセージ設計](2026-08-01-initial-message-redesign-design.md) の成果（素材外話題 8%、汎用性 26%）が
悪化しないかは、実LLM評価で確認していない。必要なら `evals/test-message-quality.ts` に
口調バリアントを足して測る（コーパスの再収集が必要）。
