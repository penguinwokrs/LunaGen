# いいね＋一言のプレミアムメッセージを500文字近くで生成する

2026-08-01

## 問題

いいね＋一言（プロフィール詳細の「いいね」→ モーダル →「プレミアムメッセージ」）で AI 生成すると、
500文字近くではなく 150〜180文字しか生成されない。

原因はプレミアム判定の失敗。`components/Content/GenerateButton.tsx:131` は

```ts
const isPremium = document.body.innerText.includes("プレミアムメッセージを送る")
```

で判定しているが、この文字列は luna-matching.com の実 UI に存在しない。
判定が常に false になり、通常の 200文字制約プロンプト（`constants.ts:32`）で生成されるため短くなる。

## 実測データ（2026-08-01、実機で確認）

生成ボタンが注入される textarea の `maxLength`:

| 画面 | placeholder | `maxLength` | 周辺文言 |
|---|---|---|---|
| いいね＋一言・プレミアムメッセージ | メッセージを入力 | **500** | `0/500`、「プレミアムメッセージは…100文字以上必要です」 |
| いいね＋一言・メッセージ付きいいね | メッセージを入力 | **200** | `0/200`、「メッセージ付きいいね」 |
| マッチ後スレッド | メッセージを入力 | **-1**（属性なし＝無制限） | なし |

- `プレミアムメッセージを送る` は上記3画面のいずれの `document.body.innerText` にも存在しない。
- いいねモーダルは3択（`button.sktuy90` プレミアム / `button.yed8mz0` メッセージ付き / `button.pgqnuw0` 通常）。
  選択前は textarea が無く、選択後にその選択肢に対応した textarea が1つだけ現れる。
- モーダル上部の `button.ey2olr0` はプロモ誘導で、押すと `luna-match.com/plan` へ飛ぶ（調査時の誤クリック注意）。

## 変更1: プレミアム判定を textarea の `maxLength` ベースにする

`GenerateButton` は対象の textarea を props で受け取っている。ページ全体のテキストではなく、
**いま生成しようとしている入力欄そのもの**の `maxLength` で判定する。

- 判定式: `maxLength >= 300` を premium とする。
  - 300 は実測値 200 と 500 の中間。属性なしの `-1` も自然に除外される。
- 上限が明示されていない入力欄（`maxLength <= 0`）に限り、囲んでいるダイアログのテキストに
  `プレミアムメッセージ` が含まれるかをフォールバックとして見る。
  - この語はプレミアム入力欄の案内文「プレミアムメッセージはあなたの想いを…100文字以上必要です」に実在し、
    メッセージ付きいいね欄（案内文は「メッセージ付きいいね」）とマッチ後スレッドには無い。
  - 上限が明示されている場合は maxLength を優先する。文言を優先すると 200文字の欄をプレミアムと
    誤判定し、生成文が切り詰められる。逆向きの誤り（プレミアム欄で短く生成）より実害が大きい。
- 判定は `utils/premium.ts` の純関数
  `isPremiumInput(maxLength: number, surroundingText?: string): boolean` として切り出し、
  `GenerateButton` からは
  `isPremiumInput(textarea.maxLength, textarea.closest("[role=dialog]")?.textContent ?? "")`
  を呼ぶだけにする（ユニットテスト可能にするため）。
- 実在しない文字列 `プレミアムメッセージを送る` による判定は削除する。

`background.ts` 側の `isPremium` の受け渡し・意味づけは変更しない。

## 変更2: プレミアム時のプロンプト矛盾を解消する

`background.ts:148-158` は premium のとき文字数制約を 490〜500 に差し替え、さらに

> 噛み合う点を2〜3個取り上げ、各点に自分の具体的な体験やエピソードを添えて掘り下げ、…

を追記する。しかし初回プロンプト本体（`constants.ts:10`）には

> 最も噛み合う1〜2点を選ぶ

が残ったままで、指示が衝突する。判定が直っても出力が短くなる要因になるため、premium 時は本体側の
この一文も置換する。

- 置換対象: `- 関係目的・役割・生活条件・嗜好 の4軸は対等。最も噛み合う1〜2点を選ぶ`
- 置換後: `- 関係目的・役割・生活条件・嗜好 の4軸は対等。噛み合う点を2〜3点選び、それぞれを掘り下げる`
- 文字数制約の置換と同様、**テンプレートに当該文字列が含まれるときだけ**置換する
  （ユーザーがオプション画面でテンプレートを編集している場合があるため）。
- 既存の「# 内容の厚み（プレミアム）」追記はそのまま残す。

あわせて、この加工処理（文字数制約の差し替え・噛み合い点数の置換・厚み指示の追記）を
`utils/premium.ts` の純関数 `applyPremiumPrompt(prompt: string): string` に切り出す。
`handleGenerateMessage` は `chrome.storage` 依存でユニットテストできないため、
加工ロジックだけを純関数にしてテスト可能にする。`background.ts` からはこの関数を呼ぶだけにし、
ログ出力（`Premium message: Limit expanded...`）は `background.ts` 側に残す。

## 変更しないもの

- 文字数の受理帯とリトライ（`background.ts:257-273`）: 490〜500、最大2回、`pickNearCap` で上限超過を避けて
  最も500に近い候補を採用。判定さえ直れば意図どおり働く。
- `openaiMaxTokens: isPremium ? 2000 : 500`。Gemini 側は `maxOutputTokens` 未指定で上限に当たらない。
- プレミアム時の目標文字数は 500 固定。textarea の実 `maxLength` を上限として動的に渡す案は、
  現状 500 以外の値が存在せず不要（YAGNI）。

## テスト

**ユニット（vitest）**

- `utils/premium.test.ts`: `isPremiumInput` が 500→true、200→false、-1→false、300→true、299→false を返す。
- `utils/premium.test.ts`: `applyPremiumPrompt(DEFAULT_PROMPT)` が
  - 490〜500 の文字数制約を含む
  - 200文字制約を含まない
  - 「最も噛み合う1〜2点を選ぶ」を含まない
  - 「# 内容の厚み（プレミアム）」を含む
  - 置換対象の文字列を持たない任意のテンプレートでも例外なく動き、文字数制約が末尾に追記される

**E2E（playwright, `e2e/generate-button.spec.ts`）**

- `luna-harness.ts` の偽ページを、`?premium=1` のとき「`プレミアムメッセージを送る` という段落を置く」から
  「textarea に `maxlength=500` を設定する」に変更する。通常時は `maxlength=200` を設定する。
- 既存の「プレミアム時もメッセージが挿入される」テストが、プロンプトに `480` を含むことを引き続き検証する。

**実機検証**

- `e2e/.profile`（デバッグ用プロファイル、gitignore 済み）に Gemini API キーを投入し、
  （キーはユーザーから受領。リポジトリ・ログ・スクショに残さない）
  プロフィール詳細 → いいね → プレミアムメッセージ → AI ボタン、で生成文字数が 490〜500 に入ることを確認する。
  **いいねの送信は行わない**（プレミアム残数を消費しないため、「入力内容を確認」以降は押さない）。
- 調査に使ったスクリプトは `test-results/premium-probe.mjs`（gitignore 配下）。実機確認手順はこれを流用する。
